# 资源站点与优选关键词：配置页交互设计

> 状态：已实现（0.3.0.0），以下与本文设计不同，以代码为准（2026-10-24 校对）：
> - **没有内置站点和关键词**：发布版的内置规则里 `sources`、`keywords` 都是空的，文中的站点1、"内置"小标、内置词都只是设计时的举例。
> - **Torznab / Jackett / Prowlarr 已砍掉**（4.3 B、5A 数据示例、第 7 节第 6 步、第 9 节的 Jackett 引导）：实测磁力质量差，也解决不了人机验证。规则里遗留的 `torznab` 源会被跳过并提示删除。
> - **添加站点只剩"粘贴网址"一种方式**：粘贴站点网址或一次搜索的结果页网址，自动识别 JSON 接口站或网页站点；识别不对时可手动调整字段（JSON）或手动填选择器（网页）。4.3 C 的"粘贴 / 复制规则片段"没有做。
> - **配置页没有"高级"分组**（第 3 节第 5 项、第 6 节的"最终合并结果"）：只有下载与媒体库、元数据（TMDb）、资源站点、优选关键词四组；`rules.json` 仍可手写，但配置页不显示路径，也没有导入导出入口。
>
> 范围：插件配置页里的"资源站点"和"优选关键词"两块，以及它们和 `rules.json` 的关系。
> 不变的核心原理：内置规则 + 覆盖层按字段叠加；`jsonApi` 用路径从 JSON 里取字段；搜索先"片名 + 关键词"优选、不够再降级。

## 1. 现在的问题

| 现状 | 对普通用户意味着什么 |
|---|---|
| 换站点地址、加新站点都要手写 `rules.json`，还要重启 Jellyfin | 绝大多数人不会去改，规则体系等于只对开发者开放 |
| 新增一个源要填 `itemsPath`、`fields.infoHash`、`statusPath` 等十几个路径 | 需要先会抓包、读 JSON，理解成本最高的一步 |
| 优选关键词是一个文本框，填了就整体替换内置值 | 填一个词就丢掉了内置的两个词，用户自己不知道；内置词以后更新也收不到 |
| 关键词既参与搜索又参与排序，每多一个词就多一轮请求 | 用户看不到这个代价，可能填十几个词把站点搜到限流 |
| 站点挂了只在"规则提示"里有一行文字 | 用户只看到"搜不到"，不知道是哪个站的问题 |

## 2. 设计理念

1. **用户面对的是"站点"，不是"规则"。** 规则拆成两半：*怎么读一个站*（适配方式，写一次、大家共用）和*用哪个站、用哪个地址*（每个人自己的选择）。配置页只让用户管后一半，前一半由插件自动识别或从社区导入。
2. **给例子，不给表单。** 让用户粘贴一个"在浏览器里搜过一次的地址"，比让他填"关键词参数名"直观得多；插件拿这个例子去试、去猜，把结果预览给用户看，用户只需要确认"对，就是这些"。
3. **能看见效果才敢改。** 每个站点都有状态灯和"测试"按钮；关键词旁边写明"每个词多搜一轮"。任何改动保存前都能预览，保存后立即生效，不用重启。
4. **默认可继承，改动可撤销。** 用户的改动只记"和内置不同的部分"，内置规则升级时没改过的地方自动跟着变；每一项都有"恢复默认"。
5. **简单的事一步做完，复杂的事留一个出口。** 90% 的人只会开关站点、改关键词；10% 的人要加新站；1% 的人要手写映射或分享规则。三层能力逐层展开，但底下是同一套数据。

## 3. 配置页结构

现在的配置页是一条长表单。建议分成几个折叠分组，顺序按"装好后最先要配的"排：

1. **下载与媒体库**：迅雷下载目录、电影库、剧集库
2. **元数据（TMDb）**：API Key、语言、接口地址、图片地址、预告片开关、清除缓存
3. **资源站点**（本文）
4. **优选关键词**（本文）
5. **高级**：规则提示、`rules.json` 所在路径、导入 / 导出、恢复全部默认

## 4. 资源站点

### 4.1 站点列表（所有用户）

```
资源站点                                          [+ 添加站点]
┌──────────────────────────────────────────────────────────────┐
│ ⠿ ● 站点1            内置   上次可用 · 0.8 秒 · 42 条   [测试] [开] ⋯ │
│ ⠿ ● 我的 Jackett       Torznab 上次可用 · 1.9 秒 · 120 条  [测试] [开] ⋯ │
│ ⠿ ○ example.com        自定义 上次失败：连接超时           [测试] [关] ⋯ │
└──────────────────────────────────────────────────────────────┘
  拖动 ⠿ 调整顺序：结果相同时排在前面的站点优先。
```

- **状态灯**：绿 = 最近一次搜索成功；黄 = 成功但 0 条结果或较慢；红 = 失败，旁边写失败原因（超时、HTTP 403、返回不是 JSON、字段找不到）。数据来自真实搜索，测试按钮也会更新它。
- **开关**：直接对应规则里的 `enabled`。关掉内置源只记一条 `{ name, enabled: false }`。
- **拖动排序**：只影响同等条件下的排序和请求顺序，不改核心逻辑。
- **⋯ 菜单**：编辑地址、测试、复制为规则片段、恢复默认（内置源）/ 删除（自定义源）。
- **测试**：用一个固定的热门片名（可改）搜一次，弹出：耗时、条数、前 5 条标题和体积。用户一眼就能判断"这个站还活着、解析对了"。

### 4.2 编辑地址（换域名，最常见的操作）

点站点名展开，只显示一个"地址"列表：

```
地址（依次尝试，上次成功的排到最前）
  https://站点1/api/search        ✓ 上次成功
  https://备用域名/api/search          [删除]
  [+ 添加备用地址]                                [恢复默认]
```

对应规则里的 `endpoints`。这是规则文件里用户唯一真正需要关心的字段，把它单独拿出来。

### 4.3 添加站点：三种方式，按难度排列

点"添加站点"后先选一种：

**A. 粘贴一次搜索的地址（推荐，给大多数人）**

> 告诉我们这个站怎么搜：在站内搜一次"流浪地球"，把浏览器地址栏的地址粘贴到这里。之后所有影片都会通过这个站点找资源。

粘贴的地址只是一个**样例**：插件从中学会"这个站怎么搜、结果怎么读"，保存的是一个全局站点（结构和内置 站点1 那一项相同），搜任何影片都会用它，"流浪地球"这次的结果本身不保存。用"流浪地球"是因为几乎每个站都搜得到，识别时一定有结果可分析。

用户粘贴的通常是**浏览器地址栏的网页地址**（如 `https://站点1/search?keyword=流浪地球`），而不是接口地址（`https://站点1/api/search?keyword=…`）。网页返回的是 HTML，所以先要找到真正的 JSON 接口。按下面四步依次尝试，前一步成功就停：

| 步骤 | 做法 | 覆盖面 |
|---|---|---|
| 1. 认识的站直接匹配 | 按域名查内置规则和社区规则（如 `站点1`），命中就直接套用现成规则，不做任何猜测 | 热门站点，零成本 |
| 2. 同域名猜接口 | 保留网页地址里的关键词参数，依次试常见接口路径：`/api/search`、`/api/v1/search`、`/api/torrents/search`、`/search.json`、原路径加 `/api` 前缀等；哪个返回带资源列表的 JSON 就用哪个 | 前端和接口路径规律一致的站，站点1 属于这一类 |
| 3. 从网页里找线索 | 读网页 HTML 和它引用的 JS 文件，提取 `/api/...`、`fetch(...)`、`axios` 等处出现的路径，带上关键词逐个试 | 大多数单页应用（SPA）型资源站；不保证成功 |
| 4. 请用户帮忙 | 带截图的引导：按 F12 → 网络（Network）→ 再搜一次 → 复制名字带 search 的那条请求地址；同时给"到社区找这个站的规则"入口 | 兜底，少数用户会用 |

识别过程逐条显示进度（"认识这个站吗… 不认识 / 正在找接口… 已找到 /api/search / 正在读取结果…"），失败时说清楚卡在哪一步。四步都失败、且网页本身就是服务端渲染的 HTML 时，提示"这个站点没有 JSON 接口，暂不支持"。

找到接口后：

1. 在接口地址的查询参数里找值等于"流浪地球"的那个，认定为关键词参数；`limit`、`offset`、`page` 等常见名字自动识别为分页参数。
2. 在返回的 JSON 里自动找映射：
   - **列表**：找最大的"对象数组"，路径即 `itemsPath`；
   - **infoHash**：值是 40 位十六进制或 32 位 Base32 的字段；**磁力**：以 `magnet:` 开头的字段；
   - **标题**：包含"流浪地球"的字符串字段；
   - **体积**：数值大于 1 MB 的数字字段（多个时取名字像 size / length 的）；
   - **时间**：像 Unix 秒或 ISO 日期的字段；
   - **文件列表**：对象数组里含路径 + 体积的字段；
   - **状态码 / 还有下一页**：顶层的 `status` / `code`、`has_more` / `hasMore` 这类常见名字。
3. 显示预览表：识别出的前 5 条（标题、体积、时间、磁力是否齐全），下面一句"识别结果看起来对吗？"→ [对，添加] [不对，手动调整]。

字段识别失败或用户点"手动调整"，进入 C。在第 2–4 步识别成功的站点，可以用"复制为规则片段"分享出去；社区收录后，其他用户在第 1 步就能直接认出这个站。

**B. ~~连接 Jackett / Prowlarr（Torznab）~~（已取消，见文首状态）**

> 只需填 Torznab 地址和 API Key。

Jackett / Prowlarr 已经适配了几百个公开和私有站点，接上一个就等于有了所有这些站点。这是用最低的理解成本换最大能力的那一步：FireFly 不用自己追每个站的改版。需要新增一种源类型 `torznab`（v6 方案"以后"里已列出），返回 XML 字段固定，不需要映射。

**C. ~~手动映射 / 粘贴规则（给少数高级用户和社区作者）~~**

- **字段映射表单**：A 自动识别的结果预填进去，每个字段旁边有一个下拉框，选项是接口返回里实际出现的路径（附示例值），用户"选"而不是"打"。右侧实时显示按当前映射解析出的前几条。
- **粘贴规则片段**：直接粘贴别人分享的 JSON 片段（就是 `sources[]` 里的一项），解析后同样先预览再添加。这是社区分享站点的主要方式，配合 ⋯ 菜单里的"复制为规则片段"形成闭环。

## 5. 优选关键词

### 5.1 交互

用标签（chip）代替文本框：

```
优选关键词                                         [恢复默认]
  [关键词1 ✕] [关键词2 ✕] [某字幕组 ✕]  [+ 添加]
  内置           内置
  搜索时会依次用"片名 + 每个词"各搜一轮，词越多越慢；建议不超过 5 个。
  排在前面的词优先级更高，可拖动调整。
```

- **内置词和自定义词放在同一排**，内置的带"内置"小标。删内置词只是把它标记为停用（灰色、可再点亮），不会让用户误以为丢了。
- **默认是"在内置基础上增减"，不是整体替换。** 存成"新增了哪些、停用了哪些、顺序如何"，以后内置词更新，用户没动过的那部分会自动跟上。
- **超过 5 个词时提示**请求次数（剧集是"词数 × 2 种季号写法"轮），并在搜索时限制最多同时用前 N 个，避免被站点限流。
- **试一试**：输入一个片名，显示"按当前关键词，优选阶段搜到 X 条"，帮用户判断这个词有没有用。

### 5.2 一个小的排序改进（可选）

现在排序只看"标题里有没有任何一个关键词"。顺序既然可以拖动，建议排序改成"命中的第一个词在列表里的位置"，让顺序真正有意义。这是对现有 `Order` 的一行级修改，不改两阶段搜索。

### 5.3 刻意不做的

v6 方案的原则是"放弃重度规则，把过滤交给上游精选站点、由用户在版本列表里自选"。所以这里**不做**正则、权重打分、排除词。如果以后确实需要"不要某个发布者"，再加一个"屏蔽词"标签行，交互和优选词一致。

## 5A. 按资源类型分站点、按站点和类型区分关键词

现实情况：电影、剧集、综艺、动漫、纪录片往往分散在不同站点，每个站点上的优选发布者也不一样（动漫看字幕组，剧集看压制组）。只有一份全局关键词、所有站点一视同仁，会让动漫站带着剧集的关键词去搜，白白多搜很多轮还搜不到。

### 理念：仍然只有"站点"和"关键词"两样东西，各加一个"适用范围"

不引入"规则组""搜索方案"之类的新概念。用户已经认识的两样东西上各多一个可选的范围标签，不设置就和今天完全一样：

| 对象 | 新增的范围 | 默认 | 例子 |
|---|---|---|---|
| 站点 | **用于哪些类型**：电影 / 剧集 / 动漫 / 综艺 / 纪录片 | 全部 | 某动漫站只勾"动漫" |
| 关键词 | **限定站点**、**限定类型**，两个都可选 | 全部站点 · 全部类型 | "示例字幕组"只用于动漫；"示例纪录片组"只用于某纪录片站 |

一次搜索实际用到的东西 = 这部片子的类型 × 开启且勾了这个类型的站点 × 对这个站点、这个类型生效的关键词。规则简单到一句话就能说清，也能直接画成一张"搜索计划"表给用户看。

### 类型怎么判断

沿用热门榜单已有的分类（`discover.categories`），用 TMDb 的类型判断，不用用户手选：

- 动漫：类型含 16（动画），电影和剧集都算；
- 纪录片：类型含 99；
- 综艺：剧集且类型含 10764（真人秀）或 10767（脱口秀）；
- 其余按 TMDb 的 movie / tv 归为电影或剧集。

获取资源抽屉顶部显示"按 动漫 搜索 · 2 个站点"，判断错了可以临时切换类型重搜。

### 交互

1. **站点列表每一行多一排类型小标签**（电影 剧集 动漫 综艺 纪录片），点一下切换，亮起的就是这个站负责的类型。一眼能看出"动漫交给谁"。
2. **站点展开后多一块"本站关键词"**：列出对这个站生效的词（全局的灰色标"通用"，本站专用的高亮），可以在这里直接添加本站专用词。它和"优选关键词"分组是同一份数据的两个视图，不是两份配置。
3. **优选关键词分组里，每个词显示它的范围**（"全部"或"仅 动漫""仅 站点1"），点词打开一个小弹层，用两排勾选框改站点和类型。新增的词默认"全部"，和今天一样。
4. **"搜索计划"预览**：在关键词分组下方，按类型分页签，列出"搜动漫时：请求 A 站（用词 X、Y）、B 站（不带词）……"，并估算请求轮数。配置得不对一眼就能看出来；某个类型没有任何站点时标红提示"将改用全部站点"。

### 数据（仍是覆盖片段，叠加规则不变）

```json
{
  "sources": [
    { "name": "站点1", "types": ["movie", "tv", "variety"] },
    { "name": "anime.example", "types": ["anime"] }
  ],
  "keywords": {
    "items": [
      { "word": "示例字幕组", "types": ["anime"] },
      { "word": "示例纪录片组", "sources": ["doc.example"], "types": ["documentary"] }
    ],
    "disable": [], "order": ["关键词1", "关键词2", "示例字幕组", "示例纪录片组"]
  }
}
```

- `types` 的取值就是 `discover.categories` 的 `key`；不写 = 全部。内置规则也可以给内置站点和内置词写上范围，社区分享的站点片段自带类型。
- 关键词的 `add` 从纯字符串扩展为 `items`（字符串或带范围的对象都认），`add` 保留兼容。

### 搜索逻辑要改的地方（两阶段原理不变）

- 优选阶段：现在是"所有关键词 × 所有站点"一起搜，改为按站点分别取生效的关键词再搜；没有生效关键词的站点在优选阶段跳过，留给降级阶段。
- 降级阶段：只请求负责这个类型的站点，不带关键词，逻辑不变。
- 排序：一条资源算不算"优选"，看它所在站点、这个类型生效的关键词，而不是全局列表。
- 兜底：某个类型没有任何站点负责时，用全部开启的站点，并在搜索计划和资源抽屉里提示。

## 6. 数据怎么存（核心原理不变）

叠加顺序从两层变成三层，合并逻辑完全复用现在的 `RulesLoader.DeepMerge` / `MergeByName`：

```
内置规则 (rules.default.json，随插件升级)
  ↓ 叠加
rules.json（手写或以后的订阅，可选，高级用户）
  ↓ 叠加
配置页的改动（插件配置里的一段 JSON，格式与 rules.json 覆盖片段相同）
```

- 配置页只写**最上面一层**，内容就是一份普通的覆盖片段，比如：
  ```json
  {
    "sources": [
      { "name": "站点1", "endpoints": ["https://新域名/api/search", "https://站点1/api/search"] },
      { "name": "我的 Jackett", "kind": "torznab", "endpoints": ["http://127.0.0.1:9117/api/v2.0/indexers/all/results/torznab"], "apiKey": "…" }
    ],
    "keywords": { "add": ["某字幕组"], "disable": ["关键词2"], "order": ["某字幕组", "关键词1"] }
  }
  ```
  `keywords` 是新加的结构，替代现在整体替换的 `publisherKeywords` 覆盖方式；`publisherKeywords` 仍然认，作为"整体替换"的老写法保留兼容。
- **为什么不直接改写 `rules.json`**：手写的文件可能有注释和用户自己的排版，程序改写会弄乱；而且以后订阅下来的规则也落在这一层，不应和界面改动混在一起。分开后，"恢复默认"只是清掉配置页那一层，手写的东西不受影响。
- **保存后立即生效**：配置保存时重新合并规则，不再要求重启 Jellyfin。`rules.json` 也顺带改成检测到文件变化就重新加载。
- **"高级"分组里显示最终合并结果**（只读，可复制），用户和社区作者能看到三层叠完之后到底是什么。
- 现有 `PluginConfiguration.PublisherKeywords` 第一次加载时迁移成 `keywords`：用户填过的词里不在内置列表里的记为新增，内置词里用户没填的记为停用，行为和今天一致。

## 9. 网页站点与人机验证（2026-10-21 补充，10-22 去掉 Jackett）

实测发现，很多磁力站没有数据接口（搜索结果直接写在网页里），还有一部分开了 Cloudflare 人机验证（插件在服务器上打不开搜索页）。只认 JSON 接口的话，"粘贴搜索地址"这条主路径对很多站走不通。补两条路：

| 站点情况 | 怎么接 |
|---|---|
| 有数据接口 | 现有的 JSON 接口类型，不变 |
| 没有接口、没开人机验证 | 新增**网页站点**类型：插件直接读搜索结果网页 |
| 开了人机验证、或接口要求签名 | 不支持。插件不绕过，识别时直接说明原因，建议换一个在浏览器里不用验证就能直接搜的站 |

入口仍然只有一个"粘贴一次搜索的地址"，插件自己判断属于哪种，用户不需要知道"接口""网页"的区别。

### 9.1 识别流程

1. 认识这个站吗（已有规则）
2. 粘贴的地址或同域名下有没有 JSON 接口
3. 网页脚本里有没有接口线索
4. **新：网页里直接有结果吗**：找到一组结构相同、包含搜索词的条目，就按网页站点处理
5. **新：磁力在哪**：条目里有 `magnet:` 链接或 40 位 hash，就在列表里取；没有就打开第一条的详情页找，找到了记为"磁力在详情页"
6. 预览前 5 条，确认后添加

失败时按原因给出不同提示：

- **开了人机验证**（403/503 且是 Cloudflare 挑战页）或**接口要求签名**：说明原因，提示这类站暂不支持（~~原设计：给"用 Jackett 接入"按钮~~，已随 Torznab 一起砍掉）
- **网页里认不出结果**：给"手动填选择器"按钮
- 不再一上来就让用户按 F12；F12 只作为最后的手段，而且说明"如果抓到的就是网页地址，说明这个站没有接口"

### 9.2 网页结果怎么自动认

- **结果条目**：在网页里找出包含搜索词的元素，向上找"同一个父节点下、结构相同、至少 3 个"的兄弟块，这些块就是结果条目
- **每条里的字段**：
  - 标题：包含搜索词的链接文字
  - 详情链接：标题链接的地址
  - 磁力：`magnet:` 链接，或文本里的 40 位 hash
  - 体积：`数字 + GB/MB/TB`
  - 时间：日期格式的文本
- **保存的规则**：生成 CSS 选择器，存成和 JSON 站点一样可读、可分享的规则片段
- **搜索地址模板**：保留用户粘贴的地址里的其他参数（排序、筛选），只把搜索词和页码换成占位符

```json
{
  "name": "example-magnet",
  "kind": "html",
  "endpoints": ["https://example.org/search?keyword={keyword}&sort=relevance&p={page}"],
  "html": {
    "item": "div.search-item",
    "title": "h3 a",
    "link": "h3 a@href",
    "size": "span.size",
    "date": "span.date",
    "magnet": "a[href^='magnet:']@href",
    "detail": false
  }
}
```

`detail` 为 `true` 时去详情页取磁力（同一个 `magnet` 选择器也用在详情页里）。`@href` 表示取属性，不写就取文字。完整字段见 [规则文件格式](规则文件格式.md#网页站点html)。

### 9.3 网页版手动调整

> 实际实现：识别失败或结果不对时打开"手动填选择器"表单，逐项填 `item`、`title`、`magnet` 等选择器并预览；下面的快照点选没有做。

自动识别不对时打开，不要求用户懂选择器：

- 左边：示例结果页的简化快照，识别出的每条结果用框标出来，各个字段用颜色标出
- 右边：每个字段一行，显示当前选择器和第 1 条的样例值。"换一个"可以在候选之间切换，"在左边点选"可以直接点网页里的文字来指定
- 底部：实时预览前 5 条，至少要有标题和磁力才能添加

### 9.4 代价与限制

- **磁力在详情页的站**：每条结果要多一次请求。只对前 20 条取详情，最多同时 3 个请求，并按 hash 缓存。站点测试和搜索计划里会显示"每次搜索约 N 次请求"
- **依赖**：网页解析用插件自带的简易解析器（`MiniHtml`），没有引入 AngleSharp，不多带 DLL
- **站点改版**：选择器会失效。状态灯显示"读不出结果"，引导用户重新识别
- **不做**：执行网页里的 JS（纯前端渲染的站）、需要登录的站、绕过人机验证
